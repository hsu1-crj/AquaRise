# 规范提交代码与开发流程

## 1. 基本原则

1. 猿舟 `master` 是团队主分支，GitHub 是查看和备份镜像。
2. 提交前先同步，提交后说明清楚修改内容。
3. 一个提交尽量只完成一个主题，不混入无关格式化或临时文件。
4. 不提交 Token、密码、私钥、个人配置、构建产物和大体积无关文件。
5. 不使用 `git push --force` 覆盖团队分支。
6. GitHub 的 Pull Request 在猿舟 GitLab 中叫 **Merge Request（MR）**。如果项目启用 MR，优先使用分支 + MR 审查；没有 MR 权限时按项目负责人要求提交。

---

## 2. 开发前检查

进入项目目录：

```bash
cd /d D:\laptop-learning\企业实训\project\issedu_ysu2026_7439
```

确认当前分支和工作区：

```bash
git branch --show-current
git status
```

开始工作前从猿舟更新：

```bash
git pull --ff-only origin master
```

如果团队采用分支开发，基于最新 `master` 创建个人分支：

```bash
git switch -c feature/功能名称
```

分支命名建议：

```text
feature/功能名称       新功能
fix/问题名称           缺陷修复
docs/文档名称          文档修改
chore/事项名称         配置或整理
```

---

## 3. 修改过程中

保持修改范围清晰：

- 不要随意移动或删除其他成员的文件；
- 不要把 IDE 配置、下载文件、日志、缓存加入提交；
- 修改前后检查文件编码和路径大小写；
- 文档修改要检查标题层级、代码块和链接；
- 二进制文件修改要确认确实需要提交，并说明用途。

随时查看修改：

```bash
git status
git diff
git diff --check
```

`git diff --check` 用于发现尾随空格等明显问题。发现不相关的修改时，不要一起提交。

---

## 4. 暂存与提交

优先指定文件暂存：

```bash
git add README.md
git add "doc/文件路径"
```

查看暂存内容：

```bash
git diff --cached --stat
git diff --cached
```

确认只包含本次任务后提交：

```bash
git commit -m "<提交类型>: <简短说明>"
```

如果一次修改包含多个相互独立的主题，应拆成多个提交。不要先执行 `git add .` 再凭感觉提交。

---

## 5. 提交信息格式

推荐格式：

```text
<type>: <简短说明>
```

常用类型：

| 类型 | 用途 | 示例 |
|---|---|---|
| `feat` | 新增功能 | `feat: 增加会议记录上传功能` |
| `fix` | 修复问题 | `fix: 修复文件路径读取错误` |
| `docs` | 文档修改 | `docs: 补充成员同步配置指南` |
| `refactor` | 重构但不改变功能 | `refactor: 整理文档目录结构` |
| `test` | 测试相关 | `test: 补充文件上传测试用例` |
| `chore` | 配置、清理、工具 | `chore: 更新项目配置` |

提交说明应回答：

- 改了什么；
- 为什么改；
- 如果有必要，如何验证。

推荐示例：

```bash
git commit -m "docs: 补充成员双仓库同步步骤"
git commit -m "fix: 修复会议记录文件命名错误"
```

不推荐：

```text
update
修改一下
最终版
test
无
```

---

## 6. 提交前检查清单

提交前必须检查：

```bash
git status
git diff --check
git diff --cached --stat
git diff --cached
```

并确认：

- [ ] 没有 Token、密码、私钥或个人账号信息；
- [ ] 没有临时文件、日志、缓存或构建产物；
- [ ] 没有误删他人文件；
- [ ] 修改内容与提交说明一致；
- [ ] 相关文档已同步更新；
- [ ] 已按项目实际条件完成必要的手动验证。

---

## 7. 推送到猿舟

直接提交到主分支时：

```bash
git pull --ff-only origin master
git push origin master
```

如果在个人分支上开发：

```bash
git push -u origin feature/功能名称
```

然后在猿舟创建 Merge Request，目标分支选择 `master`。

如果推送被拒绝，先不要强制推送：

```bash
git fetch origin --prune
git log --oneline --decorate --graph --all -15
```

确认远程有新提交后，在确认没有未提交修改的前提下执行：

```bash
git pull --rebase origin master
git push origin master
```

如果出现冲突，按 Git 提示解决后：

```bash
git add <已解决的文件>
git rebase --continue
git push origin master
```

不确定时执行：

```bash
git rebase --abort
```

恢复到 rebase 前，再联系负责人。

---

## 8. 同步到 GitHub

普通成员只需要推送猿舟。仓库负责人负责镜像同步：

```bash
git pull --ff-only origin master
git push github master
```

两边不能各自随意开发。GitHub 上如果出现独立提交，先 `git fetch github` 检查，再由负责人合并，不得直接强制覆盖。

---

## 9. Merge Request 审查规范

猿舟使用 GitLab，审核入口是 Merge Request，不是 GitHub 的 Pull Request。

创建 MR 时应填写：

- 修改背景和目标；
- 主要改动文件或功能；
- 验证步骤和结果；
- 已知限制或风险；
- 需要审查的同学。

审查者重点检查：

- 是否符合需求；
- 是否误改、误删文件；
- 是否包含敏感信息；
- 是否有明显的路径、格式或兼容性问题；
- 文档是否与代码行为一致。

作者根据意见修改后继续推送同一分支，MR 会自动更新。确认审查通过后再合并。

如果页面没有 Merge requests 菜单，可能是项目功能被关闭或账号权限不足。不要因此自行创建多个互相独立的仓库；联系项目负责人确认权限和流程。

---

## 10. 合并后的清理

MR 合并到 `master` 后，所有成员更新本地：

```bash
git switch master
git pull --ff-only origin master
```

本地不再使用的分支可以删除：

```bash
git branch -d feature/功能名称
git fetch --prune
```

删除前确认分支内容已经合并，不要删除仍在开发中的分支。

---

## 11. 紧急回退原则

发现错误提交后，不要自行重写共享 `master` 历史。优先采用新的修复提交：

```bash
git revert <提交哈希>
git push origin master
```

如果是已经合并的 MR，优先在猿舟界面或命令行生成回退提交，并在提交说明中写明原因。
